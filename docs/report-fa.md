# گزارش پیاده‌سازی — SaaS چندمستاجری ارزیابی عملکرد

> این سند خلاصه‌ی فارسی برای ارائه و دفاع است. جزئیات فنی (انگلیسی، طبق تصمیم D4) در
> [`architecture.md`](architecture.md)، [ADRها](adr) و [نتایج آزمایش‌ها](experiments/README.md) آمده است.

## ۱. آنچه ساخته شد

یک SaaS چندمستاجری برای ارزیابی عملکرد کارکنان که دقیقاً همان معماری فاز ۱ را پیاده می‌کند:

- **مونولیت ماژولار** با NestJS 11؛ هفت ماژول دامنه + هسته‌ی مشترک (tenancy-core)؛ مرزها با
  dependency-cruiser در CI اجبار می‌شود.
- **یک دیتابیس، یک schema مشترک، RLS** روی PostgreSQL 18 با `FORCE ROW LEVEL SECURITY` روی هر ۱۷
  جدول مخصوص tenant و کلیدهای خارجی ترکیبی `(tenant_id, id)`.
- **مرجع tenant = claim امضاشده‌ی JWT**؛ subdomain فقط راهنماست و باید با توکن هم‌خوان باشد.
- **پیکربندی به‌جای کد**: برندینگ، feature flag، سیاست پارامتری لایه‌ای (پیش‌فرض پلتفرم ← plan ←
  tenant) و استراتژی تأیید (یک‌مرحله‌ای/دومرحله‌ای).
- **فرانت‌اند React 19** با یک build برای همه‌ی tenantها؛ تم، زبان و جهت (فارسی RTL) در زمان اجرا.
- **کنسول پلتفرم** برای ساخت، تعلیق و تغییر plan مستاجرها.

## ۲. ادعا و اثبات

| ادعا | اثبات |
| --- | --- |
| هیچ نشتی بین tenantها رخ نمی‌دهد | ماتریس ایزولاسیون E1: ۲۲ مسیر پارامتردار با شناسه‌ی tenant دیگر ← همه 404؛ ۱۶ مسیر فهرستی ← هیچ شناسه‌ای از tenant دیگر؛ داده‌ی قربانی بایت‌به‌بایت دست‌نخورده |
| حتی اگر کد اشتباه کند، دیتابیس جلو را می‌گیرد | همان ماتریس با **خاموش‌کردن فیلتر اپلیکیشن**: باز هم 404 در همه‌جا؛ کوئری خام بدون context روی هر ۱۷ جدول: صفر ردیف |
| context روی اتصال‌های pool شده نشت نمی‌کند | ۲۰۰ عملیات هم‌زمان دو tenant روی یک pool؛ هیچ‌کدام داده‌ی دیگری را ندید |
| نقش اجرایی نمی‌تواند RLS را دور بزند | تست کاتالوگ: superuser نیست، BYPASSRLS ندارد، مالک هیچ جدولی نیست |
| ساخت tenant جدید بدون کد و بدون restart | یک فراخوان API، تراکنش اتمیک، زیر ۵ ثانیه (تست خودکار)؛ زمان واقعی هر بار روی صفحه‌ی کنسول نمایش داده می‌شود |
| یک کد، دو رفتار | ثبت ارزیابی مدیر در Acme ← `MANAGER_SUBMITTED` (تأیید لازم)؛ همان درخواست در Globex ← `PUBLISHED` |
| کد مخصوص یک tenant ممنوع است | قانون ESLint مقایسه‌ی slug/شناسه‌ی tenant با مقدار ثابت را خطای build می‌کند (در حین توسعه یک مورد در seed را گرفت) |
| مرز ماژول‌ها واقعی است | یک import غیرمجاز عمدی ← ۳ خطای dependency-cruiser و شکست build |
| audit قابل دست‌کاری نیست | نقش اجرایی فقط INSERT/SELECT دارد و trigger حتی مالک جدول را متوقف می‌کند |
| سربار RLS ناچیز است | E3: شرط RLS در شرط ایندکس ادغام می‌شود (تفاوت ±۰٫۰۶ میلی‌ثانیه، در حد نویز)؛ هزینه‌ی واقعی، رفت‌وبرگشت‌های تراکنش (حدود ۰٫۲ میلی‌ثانیه) است |
| schema مشترک انتخاب درستی است | E2: ساخت tenant حدود ۳٫۵ میلی‌ثانیه در برابر ۲۲۰ میلی‌ثانیه در schema جدا؛ migration یک‌بار در برابر N بار؛ ۸۴ شیء کاتالوگ به‌ازای هر tenant در مدل B |
| همسایه‌ی پرمصرف کنترل می‌شود (نه کامل) | E4: p95 مستاجر سبک ۲۷ میلی‌ثانیه به‌تنهایی؛ ۹۶۰ با مستاجر سنگین بدون کنترل؛ ۶۸۳ با rate limit؛ ۲۹۸ با statement_timeout. ایزولاسیون کامل منابع نیاز به ظرفیت جدا دارد (مسیر رشد مستند) |
| ایندکس‌های tenant-first لازم‌اند | E6 با ۱۰۰ tenant و ۳٫۲ میلیون نمره: صفحه‌ی audit با ایندکس tenant-first حدود ۱ میلی‌ثانیه، بدون آن ۱۶ تا ۲۴ میلی‌ثانیه و رشد خطی با تعداد tenant |

## ۳. سناریوی دمو (سه بخش، طبق سند فاز ۱)

پیش از ارائه: `pnpm db:reset` (ریست کامل + seed، هر بار از نقطه‌ی ثابت) و `pnpm dev`.
رمز همه‌ی حساب‌ها: `Demo-pass-2026`.

### دمو ۱ — ساخت tenant (RQ3)
1. `http://admin.localhost:5173` ← ورود با `platform@appraisal.test`.
2. «New tenant»: نام، subdomain (مثلاً `initech`)، plan، مدیر اولیه، رنگ‌ها، تأیید روشن.
3. «Create tenant» ← زمان ساخت روی صفحه نمایش داده می‌شود.
4. باز کردن `http://initech.localhost:5173` ← صفحه‌ی ورود با همان برندینگ؛ ورود با مدیر جدید.

### دمو ۲ — سفارشی‌سازی (RQ3)
سه پنجره‌ی هم‌زمان:
- `acme.localhost` (انگلیسی، آبی، با reports و analytics)
- `globex.localhost` (فارسی RTL، نارنجی، بدون analytics)
- در هر دو: مدیر یک ارزیابی را ثبت می‌کند. Acme ← «در انتظار تأیید»؛ Globex ← «منتشرشده».
- در Globex کارمند (`sara@globex.test`) نتیجه را نمی‌بیند (سیاست MANAGERS_ONLY).
- در تنظیمات Acme تغییر رنگ ← تم بلافاصله عوض می‌شود؛ رنگ کم‌کنتراست ← سرور رد می‌کند (WCAG).

### دمو ۳ — حمله (RQ1، RQ5)
1. توکن کاربر Acme + شناسه‌ی یک ارزیابی Globex در Postman ← `404`، با بدنه‌ی دقیقاً برابر با
   شناسه‌ی ناموجود.
2. توکن Acme روی `globex.localhost` ← `403 TENANT_MISMATCH` و رویداد امنیتی در audit مربوط به Acme.
3. فیلد اضافی `tenantId` در body ← `400`.
4. اجرای ماتریس: `pnpm --filter @appraisal/api test:int` ← هر دو حالت (با و بدون فیلتر اپلیکیشن) سبز.
5. نمایش audit log در Acme: تغییر رنگ دمو ۲ و رویدادهای امنیتی حمله.

بیمه‌ی دمو: ریست یک‌فرمانه، نمودارها و جدول‌های آماده در `docs/experiments/results`.

## ۴. یافته‌های حین پیاده‌سازی (بخشی از دفاع)

- **قانون کنتراست WCAG**: نسخه‌ی اول («بهترین متن سیاه یا سفید ≥ ۴٫۵») تقریباً هر رنگی را می‌پذیرفت؛
  تست آن را نشان داد و قانون به «کنتراست با سفید ≥ ۴٫۵ برای هر دو رنگ برند» اصلاح شد.
- **فرار promiseهای تنبل Prisma از AsyncLocalStorage**: تست همزمانی ۲۰۰ درخواستی نشان داد اگر
  callback تراکنش یک PrismaPromise را بدون await برگرداند، عملیات بیرون از تراکنش اجرا می‌شود و
  pool قفل می‌شود. همین الگو در E3 برای `runAs` هم دیده شد. هر دو اصلاح شدند و تست رگرسیون با pool
  تک‌اتصاله دارند. این دقیقاً ریسک R1 سند فاز ۱ بود و با spike و تست بسته شد.
- **بازبینی امنیتی مستقل** روی کد: نشت بین tenantها پیدا نشد، اما دو مسیر ارتقای دسترسی درون یک
  tenant پیدا شد (`user:write` می‌توانست مدیر tenant بسازد و `role:write` عملاً همه‌ی مجوزها بود) و چهار
  مورد race/لبه. همه با «سقف اعطای مجوز»، قاعده‌ی «حداقل یک مدیر فعال» زیر قفل ردیف، ایندکس یکتای
  جزئی برای «یک دوره‌ی فعال»، پنجره‌ی مهلت در چرخش refresh token و اعتبارسنجی دقیق UUID اصلاح شدند و
  هرکدام تست رگرسیون دارند.
- **وابستگی organization ← iam** اضافه شد تا ماژول سازمان مستقیماً جدول کاربران را نخواند (ADR-001).
- **maxWait پیش‌فرض Prisma (۲ ثانیه)** زیر بار انفجاری کافی نبود؛ افزایش یافت و در E3 مستند شد.

## ۵. تصمیم‌های باز فاز ۱

- **D5** (آمار بین tenantها و BYPASSRLS): بسته شد، بدون BYPASSRLS. کنسول پلتفرم فقط فهرست، وضعیت و
  plan را از جدول‌های پلتفرم نشان می‌دهد؛ آمار تجمیعی آینده از جدول شمارنده‌ی رویدادمحور (ADR-012).
- **D6** (کتابخانه‌ی UI): Tailwind 4 با چند کامپوننت ساده‌ی داخلی؛ همه‌ی رنگ‌ها از CSS variable.

## ۶. محدودیت‌ها و آینده

- rate limit درون‌حافظه‌ای است (با R نمونه تا R برابر بودجه)؛ Redis فقط هنگام نیاز به دقت.
- بازیابی جداگانه‌ی یک tenant سخت است (هزینه‌ی schema مشترک)؛ مسیر رشد: جدول directory و انتقال
  tenant بزرگ به دیتابیس اختصاصی.
- SSO، ایمیل واقعی، آپلود فایل و دامنه‌ی اختصاصی خارج از محدوده‌اند.
- فایل‌های Docker Compose نوشته شده‌اند اما روی لپ‌تاپ توسعه Docker Desktop اجرا نشد؛ همان مراحل
  به‌صورت native اجرا و تأیید شده‌اند؛ workflow ‏CI نوشته شده ولی چون مخزن push نشده هنوز اجرا نشده است.
